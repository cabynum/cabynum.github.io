![RFE Creator: from idea to board-ready Initiative](/images/rfe-creator-hero.png)

[RFE Creator](https://github.com/opendatahub-io/rfe-creator) is the component we interact with first when we need to get new work into our Agentic Development Lifecyle (ADLC). It is one of the many components on our ["factory floor"](/posts/software-factory-floor/).

In our most recent release cycle, my team noticed that some of the work we'd planned will eventually become repetitive. In fact, this particular bit of work is maintenance work that my team will have to complete with each major release cycle. Because we'd like to work smarter not harder, we decided it would be smart to open a ticket on our board to automate away as much of this specific type of work as reasonably possible.

We stashed the idea at the time so that we wouldn't have to worry about it and to focus on our deadlines, but when I began looking for an opportunity to get hands-on with our RFE Creator tooling, it resurfaced.

This post details my experience using RFE Creator for the first time, including how I decided to use the tool in my own daily workflow. I discuss the artifacts that are outputs of the tool and how that content is "scored". I also thought it'd be helpful to include the high level details for the setup involved in getting started with the tool, just in case you want to try it out for yourself.

---

## Getting my workspace set up

RFE Creator is built as a Claude Code [skill](https://docs.anthropic.com/en/docs/claude-code/skills). For me, that form-factor isn't the cleanest fit for how I use AI day to day. Typically, you won't find me developing in large code bases and submitting PRs all over the place, and because of this, I've intentionally established [my own productivity setup](/posts/from-files-to-software/) in Cursor, where I can edit files easily and enjoy a UX that matches my working style.

So the first decision that I needed to make was, how do I use the skill without disrupting too much of my setup.

The initial option would be to attempt to port the skill over and tightly integrate it with my command center in Cursor. I shied away from this because it would have meant fighting against using the skill in the way that it has clearly been designed to run - stripping away the benefits of the Claude dependency chain. Instead I opted to keep things simple and clone the [skill repository](https://github.com/opendatahub-io/rfe-creator) locally and add that repository folder to the same Cursor workspace where my "command center" lives. To run Claude Code (and in turn the RFE Creator skill), I use Cursor's integrated terminal. This setup allows me to read my markdown artifacts generated by the RFE Creator side by side while also interacting with the skill directly in the same IDE window.

Here's what's needed for the skill setup:

- Cloned rfe-creator repository
- Claude Code available in the terminal
- Jira credentials:
  - `JIRA_SERVER`
  - `JIRA_USER`
  - `JIRA_TOKEN`

## Creating my first RFE...ahem Initiative

The majority of people who decide to use the RFE Creator tool will be doing so to do just that, create an RFE. A request for enhancment is for product enhancements that have been specifically requested by a customer or a Product Manager. Because my situation was not quite that, I did not use the popular `rfe.create` command, I used the already built-in parallel functionality `/initiative-create` to create an Initiative. Its flow is `/initiative-create` → review → submit to Jira. Intiatives are meant for non-trival work that necessitates meaningful thought and structure in Jira, but isn't work for customers or specifically designed to enhance our product's feature set. This better matched the automation work that I'd identified for my team. The RFE Creator tooling handles both cases, and lands both RFEs and Initiatives in their respective Jira projects.

I thought it was worth calling out that I technically created an Initiative on my first use of the "RFE Creator" tool, not an RFE.

---

## How the create flow works

Creating initiatives begins with the `/initiative-create` command, which asks a set of clarifying questions before the tool is allowed to write anything.

The four questions asked are:

1. What is the objective?
2. What problem does this solve?
3. What is the scope boundary?
4. Is there a parent Outcome?

In my case, it prove helpful that I had existing background for the work that I was creating, which made coming up with the details need for the tool easier and faster. The related work we'd done in the prior release cycle held most of the context, so I was not starting from a blank page. I used those Jira tickets/comments along with our team commentary in Slack to round out the story. In addition to this information, the engineer that completed the initial work was diligent enough to put together a detailed report of the steps he took to complete the task which provided strong boundaries for the scope question instead of me attempting to invent them on the spot. Having gone through the end-to-end experince once now, I'd advise pulling as much of the background material together for yourself ahead of time to avoid delays and headache. It also makes for more coherent and relevant output.

## From Markdown to Jira board

The output of the `initiative-create` command is a Markdown file that is written locally to disk as a new Initiative and this file is stored under `artifacts/initiatives/`. I was able to read and edit that file as much as I wanted before anything was scored or pushed to Jira.

With the initiative Markdown saved locally, I then ran `initiative-review`. The skill expects this command to be supplied an initiative ID or a specific file, but I actually ran it without any additional arguments and it worked just fine. What happened was inference understood the job to be done from the conversation context and filled the gap for me. I didn't realize this until after the fact, but it's pretty nice nonetheless.

The review process uses a rubric to score the artifact and produces a pass/fail recommendation. Each of the five categories is worth two points:

![RFE Creator rubric categories](/images/rfe-rubric-categories.png)

My initiative scored 8 out of 10 on the first pass.

The initiative I created scored 1/2 in two of the rubric categories. For the **WHY**, a point was deducted for failing to cite customer or revenue impact, which makes sense when assessing an RFE but not for internal efficiency work like this, where there is no customer ask. The **Not a task** category also scored 1/2 because the rubric views the primary framing as process automation rather than a customer need. My scope describes business outcomes:

> - Docling container images stay current with upstream dependency and security fixes within each RHOAI release cycle, without manual multi-week maintenance efforts.
> - SDK and serve images stay in lockstep, so customers always receive a consistent pair.

Both deductions highlight the fact that the rubric is an RFE rubric. It grades for customer-driven justification and customer-facing framing because that's what RFEs are. Initiatives are different, they can be internal efficiency work with downstream customer benefits but no specific customer ask. Right now Initiatives are assessed against the same rubric as RFEs, which explains the tilt. There are plans for Initiative-specific scoring that should better handle this distinction, and I'm looking forward to seeing what that looks like.
