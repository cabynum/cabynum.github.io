![RFE Creator: from idea to board-ready Initiative](/images/rfe-creator-hero.png)

The [RFE Creator](https://github.com/opendatahub-io/rfe-creator) is the component we interact with first when we need to get new work into our Agentic Development Lifecyle (ADLC). It is one of the many components on our ["factory floor"](/posts/software-factory-floor/).

As we worked through our Feature work in our most recent release cycle, we identified some of that work as pretty  repetitive. In fact, it is work that my team will have to complete with each major release. Because we'd like to work smarter not harder, we decided we should open ticket on our board to automate away as much of the process as reasonably possible. The idea was stashed at the time, but it resurfaced as I was looking for a good opportunity to get hands-on with the RFE Creator. What follows is what that experience looked like for me, including how I decided to use the tool in my own daily workflow, what the run produced and how it "scored", and the practical setup involved if you want to try something similar.

---

## Getting my workspace set up

RFE Creator is built as a Claude Code [skill](https://docs.anthropic.com/en/docs/claude-code/skills). For me, that isn't a clean fit for how I use AI day to day. Typically, you won't fine me developing in large code bases and submitting PRs all over the place, so I intentionally established [my own productivity setup](/posts/from-files-to-software/) in Cursor, where I can edit files easily and build a UX that matches my working style.

I needed to decide how to use the skill without disrupting too much of my setup.

Porting it into Cursor for tight integration with my command center would have meant fighting a Claude Code-first plugin and dependency chain, rather than using the skill the way it was designed to run. Instead I opted to clone the [skill repository](https://github.com/opendatahub-io/rfe-creator) locally and add the folder to the same Cursor workspace where my "command center" lives. To run Claude Code (and in turn the RFE Creator skill), I use Cursor's integrated terminal. This setup allows me to read my markdown artifacts generated by the RFE Creator side by side while also interacting with the skill directly in the same IDE window.

Here's what's needed for the skill setup:

- Claude Code available in that terminal
- Jira credentials:
  - `JIRA_SERVER`
  - `JIRA_USER`
  - `JIRA_TOKEN`

## Creating my first RFE...I mean Initiative

The majority of folks that decide to use the RFE tool will be doing so to create an RFE. A request for enhancment is typically reserved for product enhancements that have been specifically requested by a customer or a Product Manager. Because my request was neither of those, I used the built in functionality to create an Initiative(`/initiative-create` → review → submit into RHOAIENG). Intiatives are bodies of work that necessitate thought and real structure, but aren't work for customers or specifically designed to enhance the product's feature set. RFE Creator handles both cases, and lands RFEs in and Initiatives in their respective Jira project.

I won't spend much time on the divergence in types of work, but it is worth calling out that I technically created an Initiative, not an RFE. The internal engineering work for is us automating recurring release maintenance for a container image my team provides, not a customer business need.

---

## How the create flow works

Creating Initiative begins with the `/initiative-create` command, which asks a set of clarifying questions before the tool is allowed to write anything.

The four questions asked are:

1. What is the objective?
2. What problem does this solve?
3. What is the scope boundary?
4. Is there a parent Outcome?

In my case, having existing background made coming up with those details easier. The Feature from the prior release cycle held most of the context, so I was not starting from a blank page. The previous work, plus commentary on those tickets and in Slack, rounded out the story. The engineer that completed the initial work was diligent enough to put together a detailed report of the steps he took to complete the task, and it provided strong boundaries for the scope question instead of me attempting to invent them on the spot.

## From markdown to the board

RFE Creator's `initiative-create` command writes a local markdown Initiative under `artifacts/initiatives/`. I was able to read and edit that file before anything was pushed to Jira.

After the Initiative was saved locally, I ran `initiative-review`. The review uses a rubric to score the artifact and produces a pass/fail recommendation. Each of the five categories is worth two points:

![RFE Creator rubric categories](/images/rfe-rubric-categories.png)

My initiative scored 8 out of 10 on the first pass.

The initiative I created scored 1/2 in two of the rubric categories. For the **WHY**, a point was deducted for failing to cite customer or revenue impact, which makes sense when assessing an RFE but not for internal efficiency work like this, where there is no customer ask. The **Not a task** category also had a 1/2 result because the scope section read more like a list of implementation activities than business outcomes:

> - Konflux pipeline components and nudging (SDK image triggers serve image rebuild), Renovate (or equivalent) for automated dependency and base-image bump PRs...
> - Encode the audit decisions from the 3.5 model audit...into configuration so routine releases do not restart model discovery from scratch.

Both deductions felt like the rubric grading me as if I had written an RFE rather than an Initiative. Right now Initiatives are assessed against the same rubric as RFEs, which likely explains the tilt. I didn't spend much time trying to correct this and moved forward with running `initiative-submit` to submit to Jira. I could have probably framed the scope as efficiency gains from the automation (saved time for the team, sharing with broader engineering teams for scaled efficiency), but it is unclear to me if those changes would have moved the needle on the score or not. Maybe I'll try that at a later date. There are plans for stronger Initiative-specific scoring coming. Until that lands, the tilt is useful feedback for the team building this component, and a useful thing for users to be aware of.
